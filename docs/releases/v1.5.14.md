Security fixes from a full audit. Install it on every server.

## What changes

- **Customers and resellers stay inside their own zones.** A new zone cannot sit inside or above another account's
  zone, nor use DNSOne's own catalog or RPZ names. A zone a customer or reseller creates is answered by this server
  at once, but reaches the resolver (forward zones, trust anchors) only after an administrator approves it under
  *Zones*; existing zones are approved by the upgrade.
- **Dynamic DNS keys stay in their names.** An update can no longer reach the zone apex by repeating the zone name,
  and a single-label dyndns2 login always finds its own zone's key.
- **Root never acts in the dnsone account's folders.** `/var/lib/dnsone` is root's; the updater, the cluster helper
  and the installer no longer write, follow or re-own anything the dnsone account could swap for a link.
- **Sign-in:** a locked account accepts no second-factor code; SSO sign-in finishes only in the browser that
  started it and needs a verified e-mail; account security (password, two-factor) changes only from the console
  with fresh proof, never with an app password.
- **Resellers** manage only accounts that still hold a customer role, and SSO never gives a reseller's account a
  wider role.
- **Settings users** (system.manage) need the matching permissions for each backup section, and administrators
  (users.manage) for cluster accounts and join keys. App passwords cannot download backups or join keys.
- **Inputs:** IPv6 scope ids are refused in every address, zone imports bound `$GENERATE` ranges and widths, regex
  rules that would match slowly are refused, AXFR imports never use this server's own addresses, and names cannot
  end in a line break.
- **Licence keys must be for DNSOne.**

## Upgrading from 1.5.13

`sudo dnsone-update` (or *Settings → Overview → Software update*). It applies migration 0010 (zone approval) and
re-owns `/var/lib/dnsone` and its folders.
